# Splouch for iOS — parity ledger

One row per feature ID in [`app.md`](https://github.com/olivierouellet/Splouch/blob/master/docs/app.md) **v3**, the behaviour contract.
That document owns *what* each feature is and whether it is required; this file owns
*whether it is implemented here, and why not* (`app.md` §0.1).

**Stack:** SwiftUI (iOS 17+), Swift 6

Status is one of `done` / `deferred` / `diverges` / `n/a — <reason>`, as `app.md` §0.1
defines them. `diverges` is built and working, but deliberately not what the contract
says, and temporary: within a release the contract absorbs it or the app reverts. IDs are the join key across
the three repos and are never renumbered — a row that goes away keeps its ID and gains
a note. Rows already marked `n/a` below are the ones the contract itself puts out of
scope for a native client; everything else starts `deferred`.

`Level` is copied from `app.md` v3 for triage only. **`app.md` is authoritative** —
if the two ever disagree, that document wins and this one is stale.

**Where things stand (2026-09-14).** `SplouchCore` is tested with `swift test` (177
tests); `SplouchUI` and the app target (`App/Splouch.xcodeproj`) build with Xcode 26.6 and
were run on the iOS 26.5 simulator against the default cloud, a local cloud and a local Pi
(recorded session). The shell is the platform's throughout: a real tab bar, a real
navigation bar, the meet pushed onto the picker's stack. Seen working on screen: the
picker as a grouped list, its branding in both orientations, the disclaimer block, the
menu and the language and server sheets; the scoreboard with names and the ticking race
clock, in portrait and landscape; results and its empty state; the schedule at the default
text size and at `accessibility-large`, where the lane rows reflow; the filter sheet's
entry field, suggestions, tokens, capsule switches and reset, with the software keyboard
up as well as the hardware one; the app icon on the home screen and in the App Library.
`P-16`'s prompt has since been run on the simulator in all five of its standings (see its
row). **Not yet exercised on screen**: the server sheet's add row and the Bonjour list (menu
items do not take scripted taps), the lane pulse, the lock flash, pull-to-refresh,
backgrounding, a light-themed meet, the landscape board header with live EVENT and
HEAT numbers in it. `L-23`'s lap count has since been run on screen in both directions (see its row). **Not yet heard**: none of the accessibility work below has been run
under VoiceOver — the labels and traits are in place and compile, but "reads sensibly" is
a judgement only the screen reader settles. Debug builds honour `SPLOUCH_SERVER`, `SPLOUCH_MEET`
and `SPLOUCH_TAB` in the launch environment and `scripts/sim-tap.sh` taps the
simulator ([docs/development.md](docs/development.md)).

Suggested order: `P-13` (handshake) → `C-01`–`C-05` (sockets) → `P-01`/`P-08` (meet
list, open a meet) → `L-01`–`L-14` (scoreboard). Results, Schedule and the `T-*`
language controls reuse all of it.

| `P-16` | A server can be added by scanning a QR code: the code opens the app, the app asks, and the server is added and selected on a yes. Without the app installed the same code lands on a web page offering the store | native-only | `done` | `ServerLink.parse` (Sources/SplouchCore/Session/ServerLink.swift) → `AppModel.openServerLink` → `ServerInvite` → `ServerInvitePrompt` on an `.alert` in `SplouchRootView`. **The link is `https://splouch.org/add?server=<origin>` and the shape is forced.** A `splouch://` scheme is opened by no stock camera — several scanners refuse a private scheme outright — and it has no answer for the case the poster is printed for, which is the spectator who *does not have the app yet*. An `https` URL has one for free: with the app installed iOS intercepts it, and without the app nothing intercepts it at all, so Safari lands on the page and the page offers the store (`P-10`'s hand-off, which is web-only and stays that way). **The host is the app's own default server** — the one URL the app ships knowing (`P-11`) — because a universal link is verified per domain and the app cannot verify a pool's Pi, which has no `https` and no certificate. So the Pi travels in the query and never in the authority, and `ServerLink.parse` takes the host from `AppModel.defaultServer`: **a server cannot mint a code that adds a different server.** The path is matched as exactly `/add` (a prefix would swallow `/address` too), the **last** `server` value wins, and credentials in the authority are refused outright. The address inside is held to exactly what a typed one is (`P-13`): `ServerAddress(typed:)`, then `P-12`'s cleartext floor — `http` only for a `.local` name, a loopback, or a private or link-local address (`ServerAddress.isLocalName`: `127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `::1`, `fc00::/7`, `fe80::/10`; widened from names-and-loopback on 2026-10-01, the same day typed addresses (`AppModel.probe`) and `/servers` entries were put under the same floor — ATS does not cover IP literals, so it was the only check they would have met. `shared/py/splouch_links.py` has to follow so the three parsers agree). ATS enforces the same floor at the socket, but only by refusing the request; a link is refused before one is made, because a printed code is a stranger's input in a way a typed address is not. **The prompt is the whole of the consent, so it is an alert and it names the address.** Over whatever is on screen — the reader was looking at a poster a moment ago and often the app was not running, so the question is the screen's only business until it is answered. It shows `ServerAddress.display`, host and port: the one thing being agreed to is which machine the app will talk to, and "Add this server?" without a name is not a question. Scanning **does nothing else at all** — no save, no select, and no request to the address either, since scanning a code is not consent to dial whatever it names. `AppModel.acceptInvite` is where `P-13`'s handshake runs. **The prompt asks only what is left to ask** (`ServerInvite.Standing`): a server offered nowhere yet asks to **add**, one already in the list but not in use asks to **switch**, and one already in use **and answering** says *You're already on this server* over one button and asks the network **nothing**. That last case matters more than it looks: routing it through the handshake would have meant a scan on a deck with bad wifi answering "cannot reach this server" over a live heat coming from that very server, which is the one reply that is simply untrue. `acceptInvite` refuses it too, so the single button is a property of the model and not of the alert. **Only while it is answering**, though — a selected server whose handshake failed asks to switch, because that is a spectator whose Pi rebooted and the useful thing is the reconnect. **A link that does not parse still raises the prompt**, carrying `badLink` or `cleartextNotLocal`: a code that opens the app and then appears to do nothing is the one outcome worse than a code that fails, because the reader cannot tell it from a dead app. **iOS specifics.** A universal link arrives as an `NSUserActivity` of type `NSUserActivityTypeBrowsingWeb`, so the app reads it with `.onContinueUserActivity` and not `.onOpenURL` — there is no custom scheme to open. `App/Splouch.entitlements` claims `applinks:splouch.org`; the debug configuration uses `App/SplouchDebug.entitlements`, which is the same domain with `?mode=developer` so a change to the host's file is not read through Apple's CDN cache. The invite lives on `AppModel`, so the question survives the picker being rebuilt under it, and it is raised at the root, so a code scanned during a meet draws over the board and leaves the meet alone until the yes. **One SwiftUI departure, visible on screen.** An alert button always dismisses its alert, and a presented alert keeps the words it was presented with — so the prompt cannot simply stay up across the handshake the way the Android dialog does. The yes is therefore deferred by one turn (`SplouchRootView.accept`) so the platform's dismissal lands first, and every change to the invite takes the alert down and puts it back up (`onChange(of: app.invite)`): the question, then `Checking…`, then the failure. The reader sees a blink between the three, and in exchange an unreachable server fails *in* the prompt, retryably, rather than dismissing and leaving the picker looking untouched. The same platform fact costs one more thing: the Android dialog disables its Cancel while the handshake runs, and an alert button here cannot be taken away from under a finger, so Cancel stays live — and `accept` therefore spends the yes only if the prompt that gave it is still on screen. A reader who changes their mind mid-handshake, or scans a second code over the first, does not get the server switched under them by an answer that arrives afterwards. **`ServerAddress` gained one thing for this**: a redundant `:443` is now dropped in `init(url:)`. `origin` already normalised it, but a scanned address is *placed* by comparing it with the ones already known, so two spellings had to be one value and not merely one `origin`. **The web half is not in this repo and the feature is inert in production without it.** The default host must serve `/.well-known/apple-app-site-association` — `application/json`, `200`, **no file extension**, no redirect — whose `applinks.details[].appIDs` names `L86UD2L8Q5.app.splouch.ios` and whose `components` claims `/add?server=…` and nothing else of the site, plus the `GET /add` page for the phone that does not have the app. Both are **written and merged in the `Splouch` repo** (`cloud/cloud_server.py` `route_aasa` / `route_add`, `tests/test_cloud_app_links.py`) and **deployed on splouch.org** (checked 2026-10-05: `/.well-known/apple-app-site-association` answers `200 application/json` with `L86UD2L8Q5.app.splouch.ios` on `/add` with a `server`, and `/add` answers `200`). Apple caches the file through its CDN, so re-check with the developer-mode entitlement above rather than by waiting. **Seen on the simulator on 2026-09-22** (iPhone 17, iOS 26.5, device language French, against a local cloud on `127.0.0.1:5055` and the local Pi on `127.0.0.1:5056`), driven with `SPLOUCH_LINK` — a debug launch variable that hands the model the link the OS would, exercising everything but Apple's own resolution, which is the only honest local test while the association file is a 404 (docs/development.md, emulator.md): the prompt over the picker naming `127.0.0.1:5056` with *Annuler · Ajouter*; **Ajouter** showing `Vérification…` in the button's place, then saving, selecting and — a Pi having one meet — opening the board straight onto it; the same code scanned again *inside* that meet drawing over the running board as *Vous êtes déjà sur ce serveur* with a single OK, and the cloud's own code there asking *Passer à ce serveur ?* with *Changer*; `https://evil.example/add?…` refused as *Impossible d'ajouter ce serveur · Ce lien ne contient pas d'adresse de serveur*; `http://192.168.1.10:5000` refused as *Le http simple n'est permis que pour les noms .local* (the rule then; a private address is accepted since 2026-10-01); and `http://127.0.0.1:5999` accepted at the prompt and failing on the handshake — *Le serveur est injoignable* under the address, the alert holding with *Annuler · Ajouter*, a second press running the handshake again, and the board behind untouched. **Not seen**: a real scan through the OS, which needs the deploy above; and an unresolvable `.local` name, which sits on `Vérification…` until `URLSession`'s own timeout rather than failing quickly — the same wait `P-13`'s typed field has, and not particular to this row.
